# План проверки MotoClub

Задача #63. Актуальная проверяемая версия — курсовой проект в `D:/University/КП СТСР/MotoClub`, а не отдельное приложение на диске E. План составлен 24 ноября 2026; фактические результаты приведены в [отчёте](test-results-2026-11-24.md). Наличие пункта в плане само по себе не означает его успешное прохождение.

## Подготовка

- Проверить ветку и отсутствие несохранённых изменений; не добавлять `.env`, рабочие документы и локальные снимки в Git.
- Использовать отдельную PostgreSQL с одноразовыми данными; рабочую базу не сбрасывать и не очищать тестовыми сценариями.
- Применить миграции, собрать API и frontend, запустить отдельный API и клиент.
- Для положительных и отрицательных проверок использовать гостя и минимум три разных аккаунта. Для модерации — отдельного модератора.
- Проверять одновременно HTTP-код, форму ответа, состояние базы через повторный запрос и видимый результат в браузере.

## Общие проверки интерфейса

- Гость видит только доступные действия; защищённые разделы объясняют необходимость входа.
- Переходы, кнопки, раскрытие форм и возврат работают; данные сохраняются после перезагрузки.
- Есть состояния загрузки, пустого результата и ошибки; повтор действительно отправляет запрос.
- Ошибки валидации видны у формы, не теряются введённые значения; успешное действие отображает сохранённые данные.
- Основные сценарии проверить при ширинах 360/390/768/1024/1440; отдельно границы 700/701/767/768 из-за смены навигации.
- Проверить светлую/тёмную/системную темы, RU/EN, длинные подписи, даты/числа/валюты и сохранение настроек.
- Проверить Tab/Shift+Tab/Enter/Space, видимость фокуса, подписи полей и переход к основному содержимому. Проверка экранным диктором и на физических телефонах записывается отдельно.
- Настоящие внешние Google OAuth и Google Maps отделять от сценариев с синтетическим ответом или без ключа.

## Запуск API-наборов

Нужны Docker Desktop, Node.js и установленные зависимости обоих пакетов. Команды ниже выполняются из папки `MotoClub`. Используйте свободные порты; имя контейнера должно принадлежать только этому запуску.

```powershell
docker run --rm -d --name motoclub-qa-nov24 -p 127.0.0.1:55438:5432 -e POSTGRES_DB=motoclub -e POSTGRES_USER=motoclub -e POSTGRES_PASSWORD=motoclub postgres:17-alpine
$env:DATABASE_URL='postgresql://motoclub:motoclub@localhost:55438/motoclub'
npm --prefix server run db:deploy
npm --prefix server run db:seed
npm --prefix server run build
$env:PORT='4314'
$env:CLIENT_ORIGIN='http://localhost:5184'
npm --prefix server start
```

Дождитесь готовности PostgreSQL перед миграциями; при необходимости проверьте её командой `docker exec motoclub-qa-nov24 pg_isready -U motoclub -d motoclub`. Обычный seed не создаёт модератора. Тестовые аккаунты QA-наборы регистрируют самостоятельно.

В другом терминале:

```powershell
$env:QA_API_URL='http://localhost:4314'
$env:QA_ALLOW_WRITES='1'
npm --prefix server run test:qa
```

Наборы `auth`, `social`, `travel`, `personal` запускаются последовательно. Любая ошибка даёт ненулевой exit code; остальные наборы при этом также выполняются. Для отдельного набора используйте `node server/scripts/qa/auth.mjs` с теми же переменными.

Для изолированного UI задайте `VITE_API_URL=http://localhost:4314` и запустите `npm run dev -- --port 5184` в отдельном терминале. Если ключ Google ограничен другим адресом, используйте отсутствие ключа для fallback, а настоящую карту проверяйте на разрешённом адресе без изменения ограничений ключа.

После проверки остановите тестовые API/frontend и выполните `docker stop motoclub-qa-nov24`. Благодаря `--rm` одноразовый контейнер и его данные удалятся. Рабочий Compose-контейнер и его volumes трогать не нужно. Тестовые наборы оставляют синтетические данные, поэтому направлять их на рабочий API нельзя.
